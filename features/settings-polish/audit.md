# Settings Screen UI Audit

- **Date:** 2026-07-04
- **Build audited:** branch `feature/session-ui-polish` @ `ec8c3ce`, debug build on a physical Samsung SM-S901B (1080×2340, ~2.75 px/dp), both themes
- **Scope:** `AppRoute.Settings` — the app's config surface (`SettingsScreen`, `SettingsRow`, `SettingsSection`) reached from the Home top-bar gear — plus its three modal pickers (`ThemePickerBottomSheet`, `LanguagePickerBottomSheet`, and the shared `LicensePickerBottomSheet`) and their shared scaffold (`AppBottomSheet`/`AppBottomSheetRow`), in both themes and both content states (populated + loading). This is the **last unpolished screen**: the hero screens, ModeSelection, and the session flow have each had a polish pass; Settings visibly predates the "Night Flight" language. Explicit questions the audit was asked to answer: **should Settings carry a background (the sky remnant)?** and **is the header right?**
- **Method:** live on-device captures (Settings light + dark, the theme picker, the language picker) plus the Home capture as the scene reference, then a multi-lens agent audit across eight dimensions — background/scene continuity, cross-app consistency, header & layout, colour/theming, typography, iconography, interaction/motion, accessibility — with a competitive/scene-grammar benchmark. **35 findings raised; every one adversarially verified against source and by re-sampling pixels from the captures and re-deriving contrast from the theme hex. 29 confirmed (after consolidating cross-lens duplicates: 2 high, 9 medium, 8 low), 1 refuted.** A handful carry an explicitly-hedged sub-claim, corrected inline. Quality bar: the shipped sibling `ModeSelection` (the screen reached from Home exactly as Settings is) as left by its polish pass, plus the same best-in-class benchmark set the prior audits used.
- **Evidence:** on-device captures at 1080×2340; pixel samples and contrast ratios quoted below were measured on those originals or computed from the theme palette in `Theme.kt` / `HorizonPalette.kt`.

> File/line references are to the audited commit and will drift.

## Verdict

Settings is **already half-polished and structurally sound** — it correctly reuses `FloatingTopBar`, `AccentIconChip`, the shared `SectionHeader`, and a clean Gemini grouped-list — but it stopped one layer short of the Night Flight pass every sibling got. The gaps cluster into three families. First, a **scene family**: Settings is the only Home-reached fork with no background, no entrance choreography, and no edge fade, so arriving from Home's glowing sky is a jump-cut to a flat surface. Second, a **fit-and-finish family** that is mostly mechanical ports of patterns the siblings already ship — mono numerals, the light-theme card hairline, press-scale, the tuned accent scale, a loading state. Third, a genuinely broken detail and two real accessibility gaps: section labels are **double-padded to 36 dp** and align to nothing; the **current pick in every modal picker is invisible to TalkBack** (colour + an undescribed check only); and the **screen title isn't a heading**. Only two items need a product/design decision (the version row's purpose, and whether to unify the three pickers' row anatomy); everything else is a direct reuse of a shipped primitive. As with the session audit, the fix list is **short in code even where it is long in findings** — most of it lands in `SettingsScreen.kt` plus the shared `AppBottomSheet`.

## The background question: yes — bring the sky remnant to Settings

**Recommendation: apply `Modifier.skyRemnant()` at the default `SKY_REMNANT_FRACTION = 0.11` to the Settings root, exactly as `ModeSelection` does — not the taller 0.30 results fraction.** This is the audit's headline finding and directly answers the brief.

**The cut is real.** `SettingsScreen.kt:72` is a bare `Column(Modifier.fillMaxSize())`. Sampled, the whole top region reads dead-flat: `#0A0A0C` from y≈30 to y≈480 in dark, flat `#F4F6FF` over the same span in light — no gradient at all. Home one screen up carries a live sky (`#C7D8F0` at y≈90 settling to `surface` by y≈320). By the scene grammar the prior audits established — **live sky = home base, sky remnant = a fork / navigation / config surface, flat = under test (exam only)** — Settings is a config surface reached from Home, i.e. precisely the class `SkyRemnant.kt:11` documents the 0.11 band for. It is currently the only such surface that terminates the scene chain in a flat cut.

**The plumbing is already proven and legibility passes in both themes.** `ModeSelection` draws its remnant *inside the same `OpaqueScreen`* wrapper Settings uses (`AppNavGraph.kt`), so predictive-back previews stay correct with zero routing changes — mirror `ModeSelectionScreen.kt:248-251` on the Settings root. Measured go/no-go: the `headlineLarge` "Settings" (onSurface) over `skyTop` is **9.99:1 light** (`#191B26` on `#AFC8E8`) and **15.7:1 dark** (`#E9E9EE` on `#0E0E22`), both far past AA; and at 0.11 the band has settled to `surface` just above the title row anyway, so the title mostly rests on plain surface. Status-bar icons are unaffected — Home already renders them over an equal-or-more-saturated sky top. **Pair it with the top-edge fade + inset (M4)**, per `SkyRemnant.kt`'s own doc, or scrolled rows shear at the band edge.

## The header question: keep the large-title pattern as-is

**Recommendation: no change to the header structure.** The empty `FloatingTopBar` (`title = {}`, no actions) with a separate `headlineLarge` "Settings" printed below is **not** redundant — it is the exact pattern the shipped sibling uses: `ModeSelectionScreen.kt:254` also passes `title = {}` and renders its subject title as `headlineLarge` below via `MasteryHeaderColumn`. The identity appears once, never doubled into the bar; Home differs only because it fills the bar with the licence selector. Adding a bar title here would be the divergence. The one real header defect is that this large title lacks `heading()` semantics — tracked as **M8**, a one-line fix — not the structure.

## What's already at the bar (keep)

- **Component reuse is right where it exists** — `FloatingTopBar` (with its own back-button `surfaceContainer` circle), `AccentIconChip` (the shared 40 dp tonal-circle recipe), the shared `SectionHeader` (routed through the app's one heading-bearing list label), and the `AppBottomSheet` scaffold are all correctly consumed, not re-implemented.
- **The Gemini grouped list is tasteful** — 28 dp outer / 6 dp inner corners with 2 dp gaps (`SettingsScreen.kt:231-240`) reads as one continuous card per section, and the dark-theme card fill separates cleanly (`surfaceContainer #1E1F22` vs `surface #0A0A0C` = 1.20:1).
- **Icon-on-circle contrast passes the 3:1 floor for all five chips in both themes** (Licence 3.9/6.7, Language 4.1/6.2, Theme 4.3/6.8, Debug 4.0/6.5, App-version 6.0/5.2 light/dark) — the accent-scale finding (M6) is about system discipline and hue-clustering, *not* a contrast failure.
- **Value/label text contrast is healthy** — `onSurfaceVariant` values on `surfaceContainer` compute to ~7.7:1 light / ~6.9:1 dark.
- **The empty-bar + large-title header** matches the sibling (see above) — a deliberate, consistent choice.
- **The disabled-language path already drops `clickable`** (`SettingsScreen.kt:257`), so a disabled row correctly degrades out of the button role rather than lying about being actionable — the a11y gap there (L4) is only the missing `disabled()` announcement, not a misrepresented control.
- **Sheet dismissal matches the bar** — the pickers flip a boolean to dismiss, exactly like the session flow's `AppBottomSheet` callers; the "abrupt close" suspicion was **refuted** (see bottom).

## High-severity findings

### H1. Settings paints no background — the flat top breaks the app-wide scene grammar
`SettingsScreen.kt:72`. Root is a bare `Column(Modifier.fillMaxSize())` with no `.skyRemnant()`, while the identically-reached `ModeSelectionScreen.kt:248-251` carries the 0.11 band inside the same `OpaqueScreen`. Sampled dead-flat `#0A0A0C` / `#F4F6FF` across the entire top region vs Home's live sky one screen up. **Fix:** add `.skyRemnant()` to the root (default fraction), mirroring the sibling; land it together with M4. Full measured go/no-go in *The background question* above. *(This is a scene-continuity gap, not a WCAG failure — but it is the single most visible break from the polished app and the brief's primary ask, so it leads.)*

### H2. The current pick in every modal picker is invisible to TalkBack
`AppBottomSheet.kt:101-106`; pickers at `ThemePickerBottomSheet.kt:73-86`, `LanguagePickerBottomSheet.kt:60-75`. The selected option is signalled **only** by a primary-tinted `Icon(Icons.Default.Check, contentDescription = null)` — a decorative glyph plus colour. The row root is a bare `.clickable` (`AppBottomSheet.kt:75`) with no `selected`/`Role.RadioButton` semantics, and the pickers pass the check via a custom `trailing` slot, never the row's built-in `selected` param. A TalkBack user opening the Theme sheet on a dark device hears "Follow system … Light … Dark" with no indication which is active. **Fails WCAG 4.1.2 (Name/Role/Value) and 1.4.1 (Use of Colour), both Level A.** **Fix:** replace the bare `.clickable` on `AppBottomSheetRow` with `Modifier.selectable(selected, role = Role.RadioButton, onClick = …)`, wrap each picker's option `Column` in `Modifier.selectableGroup()`, and have the pickers pass `selected = isSelected` instead of hand-rolling `trailing`. **Caveat (from verification):** the hand-rolled `trailing` checks currently carry `selectedMarkTag` testTags asserted by 8 UI-test assertions across three test files — the `selected` slot has no testTag, so add a `selectedMarkModifier`/testTag param to `AppBottomSheetRow` first, or the reuse breaks those tests (see L6).

## Medium-severity findings

### M1. Section labels are double-padded to 36 dp and align to nothing
`SettingsScreen.kt:203-211`. The private `SectionHeader` wrapper pads `start = 16.dp`, which stacks on the scroll `Column`'s own `start = 16.dp` (`:91`) **and** the shared `SectionHeader`'s built-in `start = 4.dp` (`SectionHeader.kt:29`) → **36 dp**. Measured left edges (both themes): card fill 16 dp, "Settings" title ~20 dp, section labels **36 dp**, row title text ~88 dp — the label aligns to none of them. The wrapper's own comment ("16 dp here + the shared 4 dp = 20 dp start") forgot the outer Column's 16 dp, so the intended 20 dp shipped as 36 dp. The sibling sits its section labels at 16+4 = 20 dp, level with its title. **Fix:** change the wrapper's `start` from `16.dp` to `0.dp` (keep `top = 24`, `bottom = 8`); `0 + 16 + 4 = 20 dp` then matches both the title and ModeSelection. Correct the stale comment. *(This is an actual layout defect, not a port — hence first among the mediums.)*

### M2. Light-theme row cards omit the hairline border and nearly vanish
`SettingsScreen.kt:221-226`. `SettingsSection` builds each row as `Surface(color = surfaceContainer)` with no `border`. In light theme `surfaceContainer #E8EBF7` vs `surface #F4F6FF` is only **1.10:1**; an edge scan shows a single-step fill transition with no `outlineVariant` pixel between card and canvas. `AppTile` solves this exact pair — its comment reads "Light tonal surfaces sit only ~1.1:1 above the pale canvas; a hairline outline gives the card a definite edge" (`AppTile.kt:66-73`) — by adding `BorderStroke(1.dp, outlineVariant)` in light and `null` in dark. Dark Settings is fine (1.20:1) and correctly needs no border. **Fix:** in `SettingsSection`'s `Surface`, `border = if (LocalIsDarkTheme.current) null else BorderStroke(1.dp, MaterialTheme.colorScheme.outlineVariant)`, mirroring `AppTile.kt:69-80`.

### M3. No entrance choreography — the list hard-pops while every sibling staggers in
`SettingsScreen.kt:87-162`. The file imports none of `rememberEntranceProgress` / `entrance` / `rememberReducedMotion`; the title, section headers, and rows render with no motion. `ModeSelection`, reached from Home identically, gates a play-once `entrancePending` (`rememberSaveable`, reduced-motion aware, `:227-231`) and staggers every child via `rememberEntranceProgress(index = …)`. Settings is the only Home-reached fork that pops in, so the transition reads as a jump-cut. **Fix:** reuse the primitives verbatim — hoist `entrancePending` + `playEntrance = entrancePending && !rememberReducedMotion()`, then wrap the title (index 0), each `SectionHeader`, and each `SettingsSection` in `Modifier.entrance(rememberEntranceProgress(index = i++, animate = playEntrance))`. Reduced-motion gating is required (Entrance's `animate = false` starts settled).

### M4. No top-edge fade and no top inset, so rows will shear under the bar once the band lands
`SettingsScreen.kt:88-91`. The scroll `Column` pads `start/end/bottom` only — no `.topEdgeFade(...)` and no `top` inset. `SkyRemnant.kt` and `TopEdgeFade.kt` both document that the remnant must be paired with a top fade + a matching `top = TOP_EDGE_FADE + 8.dp` inset, and `ModeSelectionScreen.kt:281-285` does exactly that. Without it the scroll-viewport top edge cuts a hard line across the band under the floating bar (and today the header hugs the bar ~16–24 dp tighter than the sibling's ~40 dp rested inset). **This is the required companion to H1.** **Fix:** `val fadePx = with(LocalDensity.current){ TOP_EDGE_FADE.toPx() }`; add `.topEdgeFade(fadePx)` to the scroll `Column` and set its `top = TOP_EDGE_FADE + 8.dp`. Keep the headline's own `top = 8.dp` for exact parity with the sibling (its header keeps an 8 dp inset on top of the container inset).

### M5. The Loading state renders a blank canvas — no skeleton, spinner, or busy semantics
`SettingsScreen.kt:85`. The body is gated on `if (state is SettingsUiState.Content)` with **no else branch**, so while `uiState` is `Loading` (its seeded initial value, `SettingsViewModel.kt:95`) only the title-less `FloatingTopBar` renders — a blank screen with nothing for TalkBack to announce. `ModeSelection` renders the shared `LoadingContent` (a centered `CircularProgressIndicator`, `ModeSelectionScreen.kt:265-267`) and Home renders a shimmer skeleton. **Scope correction from verification:** the licence provider is a warm in-memory flow by the time Settings is reachable, so in practice this is a brief pop-in frame, not an indefinite strand — but at least one blank frame is unconditional and there is no busy affordance. **Fix:** add the `Loading` branch rendering `LoadingContent(Modifier.fillMaxWidth().weight(1f))` (no `onBack` — it slots below the already-rendered bar), reusing the shipped primitive; optionally `Crossfade` the state switch.

### M6. Icon chips bypass the tuned AccentTones scale, so four of five use raw role tokens
`SettingsScreen.kt:115/129/143/156`. Only the Licence chip is on-system (its `visuals().color` routes through `CategoryColors.forLicense → AccentTones.Blue`); Language/Theme/Debug/App-version pass `colorScheme.primary/tertiary/secondary/onSurfaceVariant` **raw** into `AccentIconChip`. `AccentTones`/`ModeColors`/`CategoryColors` were built specifically to retire the "raw role colour per chip" pattern that the hero-H1 and ModeSelection audits removed. Measured consequence in dark: Licence (219°), Language (232°), and Debug (231°) are three near-identical blue-violet hues (ΔE ≈ 11) that read as one family; only Theme (amber) and the near-neutral App-version grey break out. **This is a system-discipline + hue-confusability gap, not a contrast failure** (all five clear 3:1). A sub-case: the Theme chip's raw `tertiary #8A5100` (light) is a hair off the app's tuned `AccentTones.Amber.light #9A5300` used by every other warm chip (ΔE 7.3; identical in dark). **Fix:** add a small `SettingsAccents` map (mirroring `ModeColors`) pulling per-theme hues from `AccentTones`, spacing Language/Debug away from the Licence blue and pointing Theme at `AccentTones.Amber`; keep Licence on `CategoryColors`. *(In release builds the Debug row is hidden, so the visible collision is two blues, not three.)*

### M7. Tappable rows have no press-scale and no Button role
`SettingsScreen.kt:255-258`. `SettingsRow` makes rows tappable with a bare `Modifier.clickable(onClick)` — ripple only, no shared `InteractionSource`, no scale, and no `Role`. The app's workhorse tile settles to 98% on press and announces itself as a button: `AppTile` holds a `MutableInteractionSource` + `rememberPressScale` applied via `graphicsLayer` (`AppTile.kt:64-88`) and sets `semantics { role = Role.Button }` with the note "M3 Surface(onClick) sets no role." Settings' rows are the whole point of the screen yet respond differently from every card elsewhere. **Fix:** give `SettingsRow` its own `MutableInteractionSource`, drive `graphicsLayer` scale from `rememberPressScale(it)`, pass it to `clickable`, and add `.semantics { role = Role.Button }` to the clickable rows — reusing `PressScale.kt` as-is. Not reduced-motion-gated (a 60 ms functional grab, matching `AppTile`).

### M8. The "Settings" title is not a heading for TalkBack
`SettingsScreen.kt:93-98`. The `headlineLarge` title carries only padding — no `semantics { heading() }` — while every section label below it *is* a heading (`SectionHeader.kt:30`), and the sibling's `headlineLarge` subject title marks itself a heading (`ModeSelectionScreen.kt:443`). Result: heading-jump navigation in TalkBack lands first on "Content" and never reaches the page's top-level title (WCAG 1.3.1). **Scope note:** the title is still read in linear order; this is a missing heading landmark, not an inversion (Compose `heading()` is level-agnostic). **Fix:** add `Modifier.semantics { heading() }` to the title `Text` — one line, matching the sibling.

### M9. Content has no width cap, so rows stretch full-bleed in landscape / on tablets
`SettingsScreen.kt:87-92`. The content `Column` is `fillMaxSize().verticalScroll(...)` with no `widthIn` and no `horizontalAlignment`; rows are plain `fillMaxWidth`. The sibling caps and centres — `ModeSelectionScreen.kt:289,293-294` sets `horizontalAlignment = CenterHorizontally` and wraps content in `Column(Modifier.widthIn(max = 480.dp))` "so the cards don't stretch full-bleed in landscape or on a tablet." Neither platform locks orientation, so a plain landscape rotation on an ordinary phone already exceeds 480 dp, leaving a 40 dp chip on the far left with a wide void before the chevron. **Fix:** reuse the sibling recipe verbatim — `CenterHorizontally` + `widthIn(max = 480.dp)` around the sections.

## Low-severity findings

### L1. The app version renders in the proportional font, not B612 Mono
`SettingsScreen.kt:282`. "1.1.0" flows through the generic `value` slot as `bodySmall` with no `fontFamily`; the app-wide rule is that every numeral wears `LocalAppFonts.current.numeric` (mastery %, counts, durations — `AppTile.kt:167`, `ModeSelectionScreen.kt:493`). **Fix:** the `value` slot also carries words (PPL(A), Polish, Dark), so don't blanket it — add an optional `valueFontFamily: FontFamily? = null` to `SettingsRow` and pass `numeric` only for the version row. *(Borderline for the "instrument readout" spirit, and the dimmest numeral on the screen — hence low.)*

### L2. Row value text is `bodySmall` (12 sp), the smallest type on the screen
`SettingsScreen.kt:284`. The actual current-setting payload a user opens Settings to read ("PPL(A)", "Polish", "Dark", "1.1.0") is one step below the shipped card secondary line (`AppTile.kt:108` uses `bodyMedium` 14 sp) and the M3 two-line-list supporting-text scale — a mild hierarchy inversion (title 16 sp, value 12 sp). Contrast is fine. It *is* internally consistent with the picker subtitles (`AppBottomSheet.kt:93`), a defensible settings-family choice. **Fix:** bump the value `Text` to `bodyMedium`; apply alongside L1 so the version reads as `bodyMedium` mono.

### L3. Bottom-sheet titles are plain Text, not headings
`ThemePickerBottomSheet.kt:55`, `LanguagePickerBottomSheet.kt:50`, `AppBottomSheet.kt:44`. The picker titles ("Theme", "Question language") render as `titleMedium` with no `heading()`, so a screen-reader user has no heading to orient to inside the modal. Diverges from the app's own `SectionHeader` heading treatment. **Fix:** fold the three identical `titleMedium`/24 dp-pad title Texts into one shared `SheetTitle` that carries `heading()` once. *(Best-practice/consistency, not a hard AA failure — small modal surface.)*

### L4. The disabled Question-language row isn't announced as disabled
`SettingsScreen.kt:251-257`. For a single-language licence the row drops `clickable` and dims to 0.5 alpha but adds no `semantics { disabled() }` and no reason text; the dimmed value falls to ~2.4:1 while still being used to *display* the current language. **Scope correction:** it correctly degrades out of the button role (so it does not misrepresent an enabled control), the dropped chevron is a non-colour cue, and WCAG 1.4.3 exempts inactive components — so this is a minor polish gap, not a clean standard failure, and the trigger isn't reachable for PPL(A). **Fix:** add `Modifier.semantics { disabled() }` when `enabled == false` and surface a short reason (e.g. "Only Polish available for this licence") as the row value.

### L5. The three pickers use three different row anatomies
`LicensePickerBottomSheet.kt:61-72` renders a two-line row with a tonal `AccentIconChip`; `ThemePickerBottomSheet.kt:66-71` renders a one-line row with a **bare uncircled** 24 dp glyph; `LanguagePickerBottomSheet.kt:57-59` renders a one-line row with **no leading element at all**. So the app's shared leading-identity chip survives in one sheet, loses its circle in the second, and vanishes in the third — visible when a user toggles between the adjacent Theme and Language rows. **Fix:** give theme and language rows the same `AccentIconChip` leading treatment the licence sheet uses (theme glyphs are ready; language can use a `Translate` glyph or a B612-Mono "PL"/"EN" code chip, consistent with the cockpit-numeral treatment), so all three sheets share one anatomy.

### L6. The pickers hand-roll slots the shared components already expose
`ThemePickerBottomSheet.kt:55`, `LanguagePickerBottomSheet.kt:50`, `LicensePickerBottomSheet.kt:51`. All three re-declare the sheet title Text instead of passing `AppBottomSheet(title = …)`, and all three pass a custom `trailing` check instead of `AppBottomSheetRow(selected = …)` — a reuse-first violation of the exact params the scaffold ships (CLAUDE.md: "do not write a second variant"). **Constraint:** the `trailing` checks carry `selectedMarkTag` testTags consumed by 8 assertions across three test files, and the built-in `selected` slot has no testTag — so the fix must **first** add a testTag param to `AppBottomSheetRow`, then collapse to `title =` / `selected =`. Pairs naturally with H2 (the `selected` slot is also the right home for the selection semantics). *(LicensePicker lives in `ui/license/`, not `ui/settings/`.)*

### L7. The App-version chip borrows the subtitle/disabled token instead of a deliberate neutral
`SettingsScreen.kt:156`. The Info chip is tinted `onSurfaceVariant` — the exact low-emphasis token used for the row subtitle — so among four hued chips the lone hueless one reads as de-emphasized rather than intentionally neutral. It clears 3:1 (6.0 light / 5.2 dark) and the row renders at full alpha (so it does **not** match the screen's real 0.5-alpha disabled look — the "reads as disabled" claim is overstated, hence PLAUSIBLE). **Fix:** if the row stays neutral, tint it with `AccentTones.Neutral` via the M6 map so it's a deliberate neutral distinct from the subtitle token.

### L8. The non-interactive version row mimics a tappable one
`SettingsScreen.kt:154-159`. The version row is the same `SettingsRow` with `onClick` omitted, so it's pixel-for-pixel a tappable row minus the chevron (its grey chip is near-identical to the tappable Debug chip), and it offers no copy affordance for a version a user may need to quote in a bug report. **Scope note (PLAUSIBLE):** a chevron-less, icon-led static version row in an About section is a standard Material/settings convention, so this is an enhancement opportunity, not a demonstrated bar violation. **Fix (product decision):** either make it useful — long-press/tap to copy "1.1.0" to the clipboard with a snackbar, reusing the clickable path — or visually de-weight it (plain leading Info glyph instead of the tonal chip) so it reads as an info line.

## Refuted

- **"Selecting a picker option snaps the sheet out with no slide-down while scrim/swipe dismissal animates."** Refuted: the polished session flow does the *same* direct-boolean-flip dismissal (`ExamScreen.kt:266-269`), and `AppBottomSheet` passes no hoisted `sheetState`, so **all** callers dismiss identically. Settings matches the bar, not below it.

## Implementation note

The work is concentrated: **M1–M9 and L1/L2/L7/L8 land entirely in `SettingsScreen.kt`** (mostly reusing `skyRemnant`/`topEdgeFade`/`Entrance`/`PressScale`/`AccentTones`/`LoadingContent` verbatim), and **H2 + L3 + L5 + L6 land in the shared `AppBottomSheet`/`AppBottomSheetRow`** (plus a one-time testTag param so the reuse doesn't break the 8 picker assertions). Two items — L5's picker-anatomy unification and L8's version-row purpose — want a quick product/design call before implementation; everything else is a direct port of a shipped primitive. Per the app's UI-changes rule, all of it is shared `commonMain`, so it applies to Android and iOS at once.
